# 法人番号・インボイス確認 MCP 外部向け概要

## 1. 要約

会社名は、たいてい少し間違っている。名刺では「(株)」になり、営業リストでは旧字体が混ざり、請求書では全角と半角が並ぶ。それでも、顧客管理、与信、請求、KYC、バックオフィスのデータベースは、正しい法人番号と正式な所在地、そして適格請求書発行事業者の登録状況を必要とする。

`@sugukuru/mcp-houjin-bangou` は、国税庁の法人番号公表情報および適格請求書発行事業者公表情報を AI エージェントから安全に使うための Model Context Protocol (MCP) サーバである。13桁の法人番号検索、法人名検索、チェックデジット検証、表記揺れ正規化、適格請求書発行事業者の登録確認（5ツール）に加え、3つの実務ワークフロー Prompts、MCP Apps UI Resources（法人カード・検索結果一覧）、Completion、Server Card を実装している。

目的は、単なる API ラッパーを出すことではない。不完全な会社情報を、公的な事実へ接続する小さな標準層を作ることにある。

## 2. 現在できること

- 13桁の法人番号から法人基本情報および変更履歴を取得する（`lookup_corporate_by_number`）。
- 会社名・都道府県コードから候補を検索する（`search_corporate_by_name`）。
- ネットワーク通信なしで法人番号（またはT番号）のチェックデジットを検証する（`validate_corporate_number`）。
- 表記揺れ（前株・後株、旧字体、全角半角等）を正規化し、最適化された検索語を生成する（`normalize_company_name`）。
- インボイス登録番号（`T`+13桁）から、適格請求書発行事業者の登録状態と基準日時点の登録有効性を確認する（`lookup_invoice_issuer`）。
- すべてのツール応答に国税庁所定または公開データ利用の出典表記（`attribution`）を必須同梱する。
- 取引先マスタ作成（`company-master-record`）、営業リスト補完（`sales-list-enrichment`）、顧客マスタ重複検知（`customer-master-dedup`）の 3 つの MCP Prompts を同梱する。
- MCP Apps UI（`ui://corporate-card/mcp-app.html`、`ui://search-results/mcp-app.html`）に対応しつつ、UI 非対応クライアントでも `structuredContent` とテキスト要約だけで完結する設計を備える。

## 3. 実務ワークフロー

```mermaid
flowchart LR
  rawInput["不完全な会社情報・請求書"] --> normalize["表記揺れ正規化"]
  normalize --> search["法人番号・所在地検索"]
  search --> invoice["インボイス登録状況確認"]
  invoice --> enrich["取引先マスタ用レコード"]
  enrich --> review["人間の最終確認"]
```

取引先マスタ作成（`company-master-record`）では、名刺や請求書のテキストから会社名を拾い、表記揺れを正規化し、法人番号と本店所在地、さらに適格請求書発行事業者の登録状況を確認して、マスタ登録用のレコードを作る。営業リスト補完（`sales-list-enrichment`）では、Excel や CSV 由来の不完全な企業名を順に照合する。顧客マスタ重複検知（`customer-master-dedup`）では、法人番号を強いキーとして使い、商号変更や本店移転の履歴も確認する。

この一連の流れは、派手な AI デモというより、事務作業の中に残っている小さな誤差を取り除く仕事である。人間が国税庁の検索画面を開き、表記を変えながら何度も試していた作業を、AI エージェントが手順として再現できるようにする。

## 4. 日本の MCP 市場の現在地

日本の MCP 市場は、まだ「導入事例が大量に積み上がった成熟市場」ではない。Claude、ChatGPT、Cursor、VS Code 系の環境を使う技術者・実務者から広がり、社内業務・SaaS 連携・公的データ接続へ伸びていく段階にある。

現時点での特徴は、次の通りである。

- MCP は「AI に外部ツールを安全に使わせる標準インターフェース」として認知されている。
- 日本語圏では、汎用デモよりも、会計、労務、行政手続、営業管理、請求、KYC などの業務データ接続に需要がある。
- 企業導入では、ツールの便利さだけでなく、セキュリティ、ログ非記録、出典、権限分離、レート制限、個人情報の扱いが問われる。
- 日本の公的データは有用だが、仕様書、利用規約、文字コード、分割取得、出典表記などの実務上の壁が残る。

この MCP は、その中で「日本の法人データ・インボイス公表データを AI エージェントが扱うための基礎部品」として置ける。

## 5. ターゲット

主な対象は、B2B 営業、CRM/ERP ベンダー、AI エージェント開発者、会計・請求 SaaS、税理士事務所、与信・KYC・バックオフィス担当者である。特に、手入力、名刺、紹介、展示会リスト、請求書、古い顧客台帳から企業データを作る現場に向いている。

より具体的には、次の層が対象になる。

- **開発者・AI エージェント利用者**: Claude、ChatGPT、Cursor、VS Code などから法人番号検索・インボイス確認を自然言語で使いたい人。
- **SaaS 事業者**: CRM、請求、会計、営業支援、与信、KYC に法人番号・T番号・所在地補完を組み込みたい企業。
- **バックオフィス部門**: 顧客マスタの重複、法人名の表記揺れ、請求先情報の不備を減らしたい担当者。
- **士業・経理領域**: 請求書、インボイス登録番号、法人実在確認、取引先管理を正確にしたい税理士・会計事務所。

## 6. 競合状況

実際の代替手段は、国税庁 API を直接叩くこと、Web 画面で手検索すること、LLM に推測させること、各社 CRM の内部名寄せ機能、または単純な API ラッパーである。

この MCP の立ち位置は、境界を正しく引くことにある。国税庁 API `target=1` が既に対応している、ひらがな・カタカナ、英大小文字、中点削除は再実装しない。逆に、前株・後株、法人種別、旧字体、NFKC、英語法人名、IVS、空白正規化など、仕様上残る実務のずれだけを T7 で補う。

差別化は、次の点にある。

- 国税庁仕様を読んだ上で、API が既にやることを重複実装しない。
- 会社名の表記揺れを、LLM の推測ではなく決定的ロジックで補正する。
- すべての出力に出典文を持たせ、利用規約上の責任を守る。
- ホスト版は国税庁の公開ダウンロードデータ（CSV）を自社 DB に取り込んで提供し、利用者が API ID を用意しなくてもすぐに使える。
- ローカル版は npm で公開し、手元の環境から直接実行できる。

## 7. 価値

価値は、検索そのものよりも、その前後にある。人間が何度も直していた会社名を、AI が安全に公的データへ接続できる。チェックデジット検証で無駄な通信を減らし、出典文で利用規約への責任を残す。

組織にとっての価値は、次のように整理できる。

- 顧客マスタ作成の手作業を減らす。
- 取引先の正式名称・所在地・インボイス登録確認を標準化する。
- AI エージェントが公的データを使う時の安全な接続点になる。
- 監査・説明・出典のある形でデータ補完を行える。

## 8. 運用形態

- **リモート接続（ホスト版）**: 公開ダウンロードデータ（CSV）を月1回取り込んだ PostgreSQL データベース（3ロール権限分離）と、Origin 検証・IP レート制限を備えた HTTP エンドポイントを提供する。
- **ローカル実行（HTTP 版）**: ローカルで HTTP サーバー（既定ポート 3001）を起動し、利用者自身の `NTA_APPLICATION_ID` を使って国税庁 Web-API に直接接続する（またはローカル PostgreSQL を参照する）。
